## 1. 市場調査サマリー

### 1.1 日本国内の市場構造

LINEは国内において圧倒的な地位を占めている。LINEヤフーの発表によれば、国内月間利用者数は2025年12月末時点で1億人を突破しており、日本人口の8割以上をカバーする生活インフラと化している。総務省の調査でも全年代で9割以上の国民が利用するメディアとされる。

一方でWhatsApp（世界で28億人超）、Telegram（2025年3月に10億人突破、2026年時点で「10億人を大きく超える」水準）、Discord（2025年12月時点で2億人規模）といった海外勢は、日本国内ではLINEの牙城の前でほぼ存在感を持てていない。この非対称性が意味することは重要である。**日本市場でLINEと同じ土俵（1対1・少人数グループの日常連絡）で正面から戦うのは、海外の巨大プレイヤーでさえ攻略できていない領域だということである。**

### 1.2 示唆

本プロジェクトが現実的に勝ち筋を作れるとすれば、LINEの牙城そのものを奪うことではなく、以下のいずれかの方向性が考えられる。

- LINEが手薄な特定セグメント（例: 部活・サークルのような「知り合いだが友達未満」の集団運営、オープンチャット的な緩い公開コミュニティ）に特化する
- プライバシー・広告非表示・軽量性など、LINEが構造的に譲れない部分（LINEヤフーは広告・決済・販促プラットフォームとしての収益構造を持つため、そこと競合しない軸）で差別化する
- 特定コミュニティ（家族・少人数の職場チームなど）向けの垂直特化ツールとして始める

「どの軸を選ぶか」はPhase 1のMVP決定で必ず一つに絞る必要がある。全軸を同時に狙うと差別化が薄まる。

## 2. 競合分析

### 2.1 LINE

| 項目 | 内容 |
|---|---|
| 長所 | 国内ほぼ全世代への普及、スタンプ文化による感情表現、通話・決済・ニュースまで統合した生活インフラ化、既読機能による安心感 |
| 短所 | 広告・販促目的の企業アカウント接点が多く煩雑、アプリが年々重量化、プライバシーポリシーへの不信感（過去に個人情報の海外委託先アクセス問題が発生）、電話番号ベースの登録による人間関係の強制的可視化 |
| UX | シンプルな1対1トーク画面を起点に、タブ切り替えでニュース・ウォレット・VOOMなど非メッセージ機能へ拡張する「スーパーアプリ」型 |
| 設計思想 | 東日本大震災を契機に「大切な人との連絡手段」として始まり、その後生活インフラへ拡張。関係性の可視化（友だち追加）を前提とした設計 |
| 成功理由 | 先行者利益による国内ネットワーク効果、スタンプという文化的発明、企業・自治体との接点による生活密着 |
| 改善できる点 | 広告・販促要素の分離、軽量化、プライバシー設計の透明性向上、非メッセージ機能の肥大化の抑制 |

### 2.2 Discord

| 項目 | 内容 |
|---|---|
| 長所 | サーバー・チャンネルによる話題ごとの構造化、ロールベースの権限管理、Bot・拡張性の高さ、ボイスチャットの常駐性（「もくもく通話」文化） |
| 短所 | 日常連絡ツールとしての「1対1のリアルな関係」には最適化されておらず親密なやりとりには不向き、UIの学習コストが高い、通知設計が複雑になりがち |
| UX | サーバー（コミュニティ）＞チャンネル（話題）＞スレッドという階層構造。テキストとボイスが常時共存 |
| 設計思想 | もともとゲーマー向けのボイスチャットツールとして誕生し、後にコミュニティ運営基盤へ拡張。「常駐する場」としての設計 |
| 成功理由 | ゲームコミュニティでの圧倒的な使いやすさから、DAOやオンラインサロン等、非ゲーム領域のコミュニティ運営基盤としても浸透 |
| 改善できる点 | 少人数の親密な関係向けのシンプルなモードの欠如、権限設計の複雑さ、初見ユーザーへの参入障壁 |

### 2.3 WhatsApp

| 項目 | 内容 |
|---|---|
| 長所 | Signal Protocolベースの標準E2EE、世界最大級の普及率、シンプルな電話帳ベースの連絡先管理、軽量な音声・ビデオ通話 |
| 短所 | Meta傘下であることによるメタデータ（誰が誰といつ話したか）の広告エコシステムへの活用懸念、日本国内ではほぼ普及していない、電話番号必須で番号非公開の運用がしづらい |
| UX | 電話帳と直結したシンプルな連絡先ベースのチャット一覧。機能追加は控えめで安定志向 |
| 設計思想 | 「広告のないシンプルなメッセージング」を掲げてスタートしたが、Meta買収後はビジネスメッセージング・広告連携が徐々に拡大 |
| 成功理由 | 早期からのクロスプラットフォーム対応、SMS代替としての圧倒的な使いやすさ、Signal Protocol採用による本文の高いセキュリティ |
| 改善できる点 | メタデータ収集への配慮、電話番号への過度な依存からの脱却 |

### 2.4 Signal

| 項目 | 内容 |
|---|---|
| 長所 | メッセージ内容だけでなくメタデータ最小化まで踏み込んだ業界最高水準のプライバシー設計、非営利運営による広告・データ販売なしの構造、オープンソースで検証可能な暗号実装 |
| 短所 | ユーザー基盤が小さくネットワーク効果が弱い（月間アクティブユーザーはおおむね4千万〜7千万人規模と見られる）、電話番号ベースの登録に起因する連絡先との強制的な紐付け、機能追加が慎重でスタンプ等の表現力に乏しい |
| UX | 装飾を排したミニマルなデザイン。プライバシー設定を自分で細かく制御できる反面、初心者にはやや無機質 |
| 設計思想 | 「セキュリティとプライバシーを一切妥協しない」という単一の価値観に振り切った設計。機能拡張よりも暗号実装の堅牢性を優先 |
| 成功理由 | セキュリティ専門家・ジャーナリスト・活動家からの支持、Signal Protocolが業界標準として他社（WhatsApp等）にも採用されるほどの信頼性 |
| 改善できる点 | 電話番号への依存軽減、表現力（スタンプ・カスタマイズ）の強化、ネットワーク効果を得るための普及施策 |

### 2.5 Telegram

| 項目 | 内容 |
|---|---|
| 長所 | 大人数グループ・チャンネル機能によるコミュニティ／メディア配信基盤としての強さ、軽量で高速な動作、クロスデバイス同期の滑らかさ、送信取り消し等の柔軟な編集機能 |
| 短所 | **通常のチャットおよびグループチャットはデフォルトでE2EEではなく**、独自プロトコルMTProtoでサーバー保存される（E2EEが有効になるのは手動設定の「シークレットチャット」のみで、かつ1対1限定）。「プライバシー重視」というイメージが独自プロトコルの実態と乖離しているとの専門家からの指摘もある |
| UX | チャット・グループ・チャンネルが同一のインターフェースに統合され、迷いが少ない。既読・入力中表示などLINE的な要素も持つ |
| 設計思想 | 検閲耐性とスピードを重視し、あえてクラウド同期（サーバー保存）を前提にすることで、あらゆるデバイスからのシームレスなアクセスを実現 |
| 成功理由 | WhatsAppのプライバシーポリシー変更騒動（2021年）の際に短期間で数千万人規模の流入を獲得するなど、競合の失点を確実に取り込む機動力、巨大グループ・チャンネル機能によるメディア化 |
| 改善できる点 | デフォルトE2EEの欠如という根本的な設計課題、プライバシー訴求と実装の整合性 |

### 2.6 iMessage

| 項目 | 内容 |
|---|---|
| 長所 | Apple製品間では標準でE2EE、既読・入力中表示・リアクション・投票等の機能性、SMSへの自動フォールバックによる到達性の担保、iMessage Contact Key Verificationによる中間者攻撃対策 |
| 短所 | Apple製品間のみが対象で、Androidとのやり取りは長らく非暗号化のSMS/MMSに依存していた（2026年5月にiOS 26.5でRCSのクロスプラットフォームE2EEがベータロールアウトを開始し、この制約は解消されつつある）、他OSでは利用不可という閉鎖性 |
| UX | 電話の「メッセージ」アプリに統合され、独立したアプリを起動する必要がない。OSレベルの統合による自然な体験 |
| 設計思想 | 個別アプリではなくOS標準機能として設計し、ハードウェアとの垂直統合によりシームレスな体験を実現 |
| 成功理由 | Apple製品ユーザー同士での圧倒的な使いやすさとブランドロイヤルティの強化（グループ内で自分だけAndroidだと「緑の吹き出し」になる社会的圧力すら生んだ） |
| 改善できる点 | クロスプラットフォーム対応の遅れ（現在進行形で改善中） |

### 2.7 横断比較表

| サービス | デフォルトE2EE | 登録方式 | 強み | 主戦場 |
|---|---|---|---|---|
| LINE | 通信は暗号化、E2EEは「Letter Sealing」機能としてオプトイン的位置づけ | 電話番号 | 生活インフラ化 | 日本国内の全世代 |
| Discord | なし（サーバー保存） | メール/ユーザー名 | コミュニティ運営 | ゲーマー・オンラインコミュニティ |
| WhatsApp | あり（Signal Protocol） | 電話番号 | グローバル普及 | 世界（除く日本・中国） |
| Signal | あり（Signal Protocol、メタデータ最小化） | 電話番号 | プライバシー最優先 | プライバシー意識の高い層 |
| Telegram | 通常チャットはなし（MTProto、サーバー保存）／シークレットチャットのみあり | 電話番号 | 大規模グループ・配信 | グローバル、特にインド・中東 |
| iMessage | あり（Apple製品間） | Apple ID/電話番号 | OS統合体験 | Apple製品ユーザー |

## 3. 各社から抽出すべき設計原則

1. **E2EEは「オプション」ではなく「デフォルト」にすべきである。** Telegramの通常チャットが非E2EEである点は、専門家から一貫して批判されている。設計書で既に「E2EEを前提に設計」と明記されている方針は妥当であり、Signal/WhatsAppに倣うべきである。
2. **電話番号への依存は、日本の「知り合い以外にも番号を教えたくない」という文化的抵抗感と衝突する。** LINE自体も電話番号registrationだが、友だち追加はQR/ID交換が主流であり、電話番号を直接晒さない設計になっている。この点は要件定義で明確に踏襲すべきである。
3. **「親密な関係向けUI」と「コミュニティ運営UI」は別物として設計すべきである。** DiscordとLINEが異なるUIパラダイムを持つのは必然であり、本プロジェクトが両方を志向するなら、画面遷移レベルで明確に分離する必要がある（Phase 5で詳細検討）。
4. **機動力のある差別化はプラットフォームの失点時に効く。** Telegramの急成長は競合の炎上時に集中している。長期的な安定運営に加え、競合の弱点（LINEの広告・重さ、Discordの複雑さ）を継続的に観察する体制が有効である。

## 4. 要求分析

### 4.1 ターゲットユーザー像（暫定）

- 家族: 高齢層〜若年層まで、最もリテラシー差が大きいセグメント。シンプルさと信頼性が最優先。
- 友人: LINEからの移行障壁が最も高いセグメント（相手も使っていないと成立しないネットワーク効果の壁）。
- 学校・部活・サークル: 未成年ユーザーを含む可能性が高く、安全設計（通報・ブロック・管理者権限）が必須。
- 職場: 既読管理・スレッド・ファイル共有など「業務利用」に耐える機能が必要になりうるが、Slack/Teamsとの機能競合にも注意。
- オープンチャット・公開コミュニティ: 匿名性とモデレーションのバランスが必要で、上記4セグメントとは異なるリスクプロファイルを持つ。

### 4.2 コア要求（設計書からの抽出）

- 1対1・グループでのテキスト/画像/動画/音声メッセージ
- E2EEによる本文保護
- オープンチャット的な公開コミュニティ機能
- 高速・軽量な動作
- 管理・拡張のしやすさ

### 4.3 非機能要求

- セキュリティ: OWASP Top 10対応、TLS、E2EE、監査ログ
- パフォーマンス: 大量ユーザー下でも快適な応答性
- 可用性: メッセージ到達の確実性（信頼性はメッセージングアプリの生命線であり、未達・既読バグは即離脱に直結する）
- 保守性: Clean Architecture、型安全、DRY/KISS/SOLID準拠
- コスト: 無料運用を最優先（4.4で詳述する制約と表裏一体）

### 4.4 Phase 1で必ず決定すべき論点（未決事項）

以下は本ドキュメントでは決定せず、Phase 1で選択肢を提示し、承認を得たうえで確定する。

| 論点 | 選択肢の例 | 影響範囲 |
|---|---|---|
| MVPの対象セグメント | 家族・友人向けの少人数チャットに絞る／最初からオープンチャットも含める | アーキテクチャ、モデレーション設計、開発工数 |
| スケール想定 | 個人〜数百人規模の検証運用／数千人規模の本番運用 | インフラ選定、無料枠との整合性 |
| E2EEの適用範囲 | 全チャット（グループ含む）に適用／1対1のみ先行実装 | 暗号設計の複雑度、開発期間 |
| 未成年ユーザーへの対応 | 年齢確認・保護者機能を最初から実装／将来機能として後回し | 法務対応、Phase 1の要件定義 |
| クロスプラットフォーム範囲 | Web/iOS/Androidを最初から並行開発／Webから先行 | 開発リソース配分、Phase 6以降のディレクトリ構成 |

## 5. Phase 0 まとめ

### 実施内容
- LINE / Discord / WhatsApp / Signal / Telegram / iMessage の6サービスについて、長所・短所・UX・設計思想・成功理由・改善点を整理した。
- 最新の市場データ（LINE国内1億ユーザー突破、Discord約2億人、Telegram10億人超、Signal数千万人規模、iMessageのRCS E2EE対応開始など）をWeb検索で確認したうえで反映した。
- 各社から抽出すべき設計原則を4点にまとめた。
- ターゲットユーザー像とコア要求・非機能要求を暫定整理した。

### 設計判断
- E2EEはデフォルト適用とする方針を支持する（Telegramの反面教師的事例を根拠とする）。
- 電話番号を必須の連絡先交換手段にしない方針を推奨する（LINEのQR/ID文化を踏襲）。
- 「親密な関係向け」と「オープンコミュニティ向け」のUIは、Phase 5で明確に分離設計する前提を置く。

### 残課題（率直な指摘の再掲）
- 「無料運用最優先」と「大量ユーザー対応」の両立という根本的な制約は未解決である。Phase 1でMVPのスケール想定を確定させない限り、Phase 2のアーキテクチャ設計は着手できない。
- 「LINEより全方位で優れる」という目標は、差別化軸を絞らない限り実現可能性が低い。Phase 1で軸を1〜2本に絞る意思決定が必要である。
- 未成年ユーザーが利用対象に含まれることへの安全設計・法的配慮が、現時点の設計書には明記されていない。

### 次のPhase（Phase 1）で行うこと
- 上記「4.4 Phase 1で必ず決定すべき論点」について、選択肢と推奨案を提示し、承認を得る。
- MVPの機能範囲を確定する。
- 将来機能一覧を整理する。
